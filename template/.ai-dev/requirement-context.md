# 需求上下文与业务注释

主 Agent 在真实业务项目根目录维护 `.rag-context/<具体需求名称>.md`，使用 [摘要模板](templates/requirement-context.md)。它用于后续开发、排查和交接时恢复上下文；PRD、确认记录、intake/delivery、接口契约和当前代码仍是核查依据。摘要不是新的需求来源，也不代替技术方案、验收报告或人工批准。

## 文件归属

- 一个需求维护一份摘要，记录需求 ID 和对应 feature 路径；只读取当前需求的摘要，不把其他需求的结论混进来。
- 文件名保留具体需求名称，将路径分隔符和非法文件名字符替换为 `-`。同名但不同需求在文件名附加需求 ID，不覆盖已有文件。建立后保持路径稳定，改名先更新正文标题与来源关联。
- 摘要放在 `status.json.project.root` 对应项目的 `.rag-context/`，不要在工作流工具仓库或 feature 目录另存一份业务摘要。
- 主 Agent 编辑摘要；独立 reviewer 核查并给出修正意见，不替作者改摘要或确认业务。

## 何时更新

| 时机 | 同步内容 |
| --- | --- |
| 需求分析、规则确认后 | 目标、适用范围、已确认规则、来源和待确认问题。尚未确定的技术方案明确标为未确定 |
| spec/plan 形成或发生变化时 | 已采用的方案、页面/接口/文件、决策原因和确认依据；计划中的实现不能写成已完成 |
| 每个任务实现完成、运行验收前 | 本任务实际落地的文件/函数、已调整规则及剩余问题，清除已废弃方案的当前描述 |
| 全部开发完成、整单验收前 | 逐项对照最终代码、调用方和确认资料，检查页面、接口、状态、边界与注释；记录实际核对时间、范围和未核实事项 |
| 审核或验收后又修改代码/规则 | 重新同步相关部分，再执行受影响的测试与审核，不能沿用旧的“最终已核对”结论 |

局部变化只更新受影响部分，不追加聊天流水。已被替代的方案从当前描述中移除；若保留其决策背景，明确标为“已废弃”，写明替代方案与依据。

## 写什么、依据是什么

保留模板的六部分：需求目标、已确认的业务规则、技术实现、重要决策、待确认问题、信息依据。无相关内容时说明实际状态，不为填满模板编造结论。

- 业务规则写清触发条件、结果、边界和例外，关联确认资料或决定。未经确认的推测只能进入待确认问题。
- 技术实现区分“计划采用”“当前已实现”“尚未核实”。用项目相对文件路径和关键函数/组件定位；需要行号时必须核实，避免只写容易失效的行号。
- 重要决策说明实际采用原因与限制。产品取舍需要真实确认来源；Agent 在授权范围内作出的技术选择标为“实现决策”，不能冒称用户已确认。
- 待确认问题保留缺失依据及影响，解决后将结论及依据同步到相应部分。未回答、超时或文档名中的“最新”都不等于确认。
- 信息依据尽量链接本地需求清洗副本、确认记录、接口契约、intake/delivery 和当前代码。相对链接须从摘要文件所在目录解析；不复制凭据、完整聊天或无关个人信息。
- 后续会话先读摘要定位材料，再检查对应原文和当前代码。没有核对就保留“待核对”，不能用更新时间或“已完成”字样证明准确。

## 接入现有任务与审核

1. 在 plan 中把摘要的项目相对路径列入会更新它的任务 `files`。已有任务需补入时，按现有产物一致性与计划审核流程处理。摘要在分析期已存在，后续任务通常使用 `modify`。
2. 对根目录 `.rag-context/` 的编辑按普通项目文件处理，不能直接把该路径交给只处理 feature 内产物的 `update-consistency.mjs`。业务规则或方案变化时先更新权威产物并执行原有 mark/resolve，再同步摘要；不能只改摘要来绕过审核。
3. 在任务测试前完成摘要更新，随后运行任务检查并交审；整单测试前完成最终代码核对。摘要会参与项目快照，测试后再改它可能使结果过期，因此不要在摘要中反复抄写本轮测试结果。测试结果保留在原验证产物中。
4. `record-code-changes.mjs` 的本需求文件清单包含摘要。审核包将摘要作为待核查的 `implementation` 材料，并带上相关原始依据；不要用摘要本身证明一条业务规则已经确认。摘要变化后重新封存受影响的审核材料。
5. 在现有审核规则下增加直接检查：task 的 `SPEC-COVERAGE` / `CODE-QUALITY`、final 的 `FINAL-TRACE` / `FINAL-QUALITY` 核对摘要与实际实现、依据及注释是否一致。缺失或失实回主 Agent 修正；需要业务选择的事项留给人。

这是 Agent 执行规范与独立审核要求。现有脚本负责文件/版本证据，不会从自然语言自动判定摘要是否语义正确；没有新增独立状态、审批阶段或向量检索服务。历史已完成需求不为此自动重开，进行中的需求在后续计划/任务/最终审核中补齐对应材料。

## 中文业务注释

在本次修改涉及的复杂业务判断、容易误解的边界和特殊处理处补简短中文注释，重点解释“为什么这样处理、受什么业务条件限制”。简单赋值、明显流程和逐行代码翻译无需注释；不为满足规则给所有函数加模板注释。

例如已确认“批改失败转自评”时，可以在降级分支说明该业务限制；未确认重试次数时，不能把猜测写成产品规则。可核实的技术原因按实际代码说明，未确认的业务原因列到摘要的待确认问题中。规则变化时同步修改或删除失效注释，仅处理本次范围内的代码。
