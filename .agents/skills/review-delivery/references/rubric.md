# 审核准则

## 标准来源

已确认需求/人工决策定义业务预期，接口契约定义输入输出，项目规则定义工程要求。实现和现有测试仅是被核查对象，不能证明需求本身正确。来源冲突且影响本次范围时需要业务决策，不擅自确定优先级。

## 阶段核查

| 阶段 | 重点 | 不应要求 |
|---|---|---|
| scope | 来源可追踪、前后端职责、未决范围 | 代码已完成 |
| spec | 页面状态、交互、异常、契约、验收覆盖 | 把推测当确认 |
| plan | 文件符号真实存在、任务依赖、验证可执行 | 个人偏好架构 |
| task | 当前任务功能、相关调用方、回归风险 | 范围外功能 |
| final | 完整改动对齐需求、原生检查与残留风险 | 未授权发布 |

## 分流规则

| 结论 | 真实场景 | 下一步 |
|---|---|---|
| revise | 要求跳过全部被占用答卷，代码只跳一次；规则明确 | Agent 修复并补连续占用/全占用测试 |
| needs_evidence | 测试未跑、接口样例待查、日志过期 | Agent 先查仓库/补本地验证，再制包 |
| needs_human | 重试次数没有产品决定；接口语义冲突；需新增生产权限 | 给人最小问题、选项、影响及已查证据 |
| pass | 本次检查完成且证据充分，无阻塞问题 | 返回建议，遵守既有流程准入 |

缺证据本身不等于需要人；只有已尝试安全替代仍需人工权限/业务确认时升级。无关的新功能建议标为非阻塞，不要求人为本次任务决策。多轮不收敛先定位分歧：技术缺陷仍修复，不能只因达到次数而让人背书；确实需要取舍才升级并提供双方证据。

严重度：blocking=本次交付无法使用或有关键安全/数据风险；major=违反确认验收或明显回归；minor=不阻塞验收的局部建议。不把缺少自己喜欢的抽象、没有需求依据的功能或无复现猜想写成 major。

每个 finding 必须有对应检查和证据。综合结论优先级为 needs_human > needs_evidence > revise > pass；保留全部问题，不能因一个人工问题隐藏代码缺陷。
