## 3. 环境、数据及可执行约束

### 3.1 计划环境

- `environmentId: profile-contract-mock`；`kind: contract-mock`。启动将来要验收的真实前端候选，使用真实页面及应用请求逻辑，只在 `/api/profile` 的网络边界直接 fulfill。
- `baseURL`、`projectName`、启动命令、测试目录及锁定的 Playwright 版本尚未提供；不能假装已存在。确认后以项目原有惯例填写。当前 `index.html` 是入口定位材料，不代表已经具备新增重试能力的可验收候选。
- `webServer.reuseExistingServer=false`；端口冲突直接报环境错误，避免误验别的服务。每个用例使用独立浏览器 context，并清理路由、请求计数和测试状态。
- 后端新功能未部署，不能依赖 `route.fetch()` 或真实服务返回再篡改。只替换确认的端点，不用宽泛 `**/api/**` 或页面级假逻辑代替真实调用链。
- 请求拦截匹配方法及完整 URL。路径已知，方法、查询参数和基准 URL 仍待 Q-01。不能因现有 `fetch` 调用省略了 method 就把 GET 写成权威契约。
- 无 live-test 结果。本次原始范围为前端设计，不擅自增加一个必须通过的真实后端集成用例；若后续范围包含 live-test，需新增独立 environment、TC 和 check，禁用响应替换，并单独准备可重置数据。

| DATA-HTTP-400 / 503 / 300 | 确认格式的响应体，状态分别覆盖客户端错误、服务错误及 2xx 上界外侧 | 格式待 Q-01；状态是故障注入选择，不声称服务平常会返回这些值 |

冻结契约后，`verification.inputs` 引用实际项目/feature 中的来源副本，环境 inputs 引用实际配置与 fixture；不要把这份输出目录当成运行器的已确认输入。此时才可填写 `contract: {path, sha256}`、实际 dataRef 路径及 fixture 路径。任何未解决变量均阻止相应测试入准，不是 `passed` 或 `skipped`。

### 3.3 拦截与计数方案

单个精确路由分发器按预设响应阶段工作，各阶段具有独立 mock rule ID；同一路径的规则不要互相覆盖。每个用例只登记自己实际需要的规则。

| 规则 ID | 精确边界 | 处理 |
| --- | --- | --- |
| MR-OK-A | CONTRACT-PROFILE.method + 已确认的完整 URL | pending，release 后返回 P_A |
| MR-FAIL-400 | 同上 | 返回 400 及已确认格式的错误体 |
| MR-FAIL-503 | 同上 | 返回 503 及已确认格式的错误体 |
| MR-FAIL-300 | 同上 | 返回最终 300；不设置引发后续重定向的 Location |
| MR-RETRY-OK-B | 同上 | 重试请求保持 pending，release 后返回 P_B |
| MR-RETRY-FAIL-503 | 同上 | 首次重试返回 503 |

记录每次真实拦截的时间、method、URL、参数、命中的规则和完成时刻，计算 pending 窗口内的请求数、最大同时在途数。不要只检查 helper 的 `isLoading()` 或 mock 函数调用次数。

每个 browser 用例 afterEach 附 `acceptance-context`，字段来自实际运行：environmentId、baseURL、注册的 mockedRoutes、各规则实际 mockHits。所声明规则必须各命中至少一次；失败也保留附件。零命中、页面未加载、未触发请求都不是业务通过。

### 3.4 断言绑定原则

- 状态和内容定位优先利用实际入口的 `#status`、`#data` 与按钮可访问名称“加载”“重试”；新增重试控件的最终定位在候选就绪后确认。
- 预期为“加载中 / 成功 / 失败”的语义状态，不锁死源码中的 `loading`、`success`、`failed: ...` 字符串。实现测试时把实际可见文案/语义属性绑定到这三个已明确的状态；绑定仅负责定位和读取，不实现一份与应用条件相同的 expected 函数。
- 资料断言优先解析显示的 JSON 与权威成功 fixture 的对应资料比较，允许等价 JSON 排版；不得用 `JSON.stringify(..., null, 2)` 的源码结果作为独立业务预期。若契约存在 envelope，需先由 Q-01 明确展示的是哪个资料部分。
- 使用真实点击和 web-first 断言。等待已拦截请求、可见状态及 release 事件，不用随意 sleep。测试超时仅为执行保护，不是业务响应时限。
- 加载时可通过禁用/隐藏入口或复用 in-flight 满足“不并行”。可用控件必须真实点击；不可用控件记录不可操作状态与网络不增，不用 force、直接调用 handler 或注入函数绕过 UI。

### TC-01：加载中及成功资料展示

前置：新 context，打开真实页面；已确认 P_A，MR-OK-A 能命中并保持请求 pending。

步骤：

1. 记录操作前请求基数，点击“加载”，等待匹配请求实际到达并保持。
2. 在未返回响应时读取状态。
3. release P_A；等待真实 UI 更新。

预期：

- E-01-01 `network`：本次操作发起契约正确的 `/api/profile` 请求，MR-OK-A 实际命中。依据 FR-06。
- E-01-02 `ui`：pending 时状态表示加载中。依据 FR-01。
- E-01-03 `ui`：响应后状态成功，资料区域展示与 P_A 对应的 JSON。依据 FR-02。

这覆盖 PRD 已明确的成功路径；外观、JSON 缩进或其他“与基线一致”的细节仍受 Q-02 限制，不能声称全面视觉回归已完成。

### TC-02、TC-03、TC-04：不同非 2xx 故障后的真实恢复

三例步骤相同，但故障分别为 400、503、最终 300，分别记录结果。

前置：新 context；失败规则及 MR-RETRY-OK-B 已按阶段配置；P_B 已确认；300 例确保观察到的最终响应确为 300，不能让后续 200 重定向掩盖故障。

步骤：

1. 点击加载；等待真实请求命中本例失败规则并返回。
2. 确认失败信息和可操作重试，记录当前请求数 N。
3. 在点击前安装新请求观察，真实点击“重试”；等待新的匹配请求，先保持 pending。
4. release P_B，等待 UI 成功。

预期（各例分别编号 `E-02-*`、`E-03-*`、`E-04-*`）：

- `*-01 network`：本例故障规则实际命中，真实响应状态为指定非 2xx。不能只凭错误条出现断言已注入成功。依据 FR-03 的故障前置。
- `*-02 ui`：加载态结束，进入失败态，失败信息可见且非空，重试可操作。具体错误文案不在断言中自行规定。依据 FR-03。
- `*-03 network`：用户重试后请求数相对 N 增加 1；新请求契约正确，MR-RETRY-OK-B 命中。不能仅重复渲染旧失败/旧成功结果。依据 FR-04、FR-06。
- `*-04 ui`：新响应到达后显示 P_B 并处于成功状态，上一轮失败状态不再显示为当前状态。依据 FR-04。

请求数的观察窗口是操作前到受控重试请求 pending；不擅自将“无自动轮询”扩展成任意时长内绝无任何自动重试的规则。若候选含自动重试且影响这条用户流程，应按 Q-06 先澄清，不悄悄改断言。

### TC-05：重试再次失败后仍可恢复

前置：新 context；响应计划依次为初次 503、首次重试 503、再次重试 P_B。

步骤：加载并到达失败；点击重试，再次到达失败；再次点击重试并返回 P_B。

预期：

- E-05-01 `network`：三阶段各自的实际请求命中对应规则，方法/URL/参数符合契约；每次用户重试确实新增请求。依据 FR-04、FR-06。
- E-05-02 `ui`：两次失败均有失败信息及可操作重试，不因曾经重试过而卡在 loading 或失去恢复能力。依据 FR-03，“请求失败”同样适用于重试请求。
- E-05-03 `ui`：最后成功展示 P_B，当前状态不再失败。依据 FR-04。

这里的两次失败是有限场景选择，不是产品重试上限，也未定义自动重试次数。

### TC-06：首次加载 pending 时重复操作不并发

前置：新 context；第一次资料响应通过 MR-OK-A 保持 pending。

步骤：点击加载；等待请求到达及加载中；连续尝试三次“加载”，并尝试当前 UI 若提供的“重试”；每次操作后观察请求计数；最后 release P_A。

预期：

- E-06-01 `ui`：响应仍未返回时可观察为加载中。依据 FR-01。
- E-06-02 `network`：相对本次开始的计数，pending 窗口内只有原来的 1 个资料请求，最大在途数为 1；没有第二个并行请求。依据 FR-05。
- E-06-03 `ui`：不可操作入口的隐藏/禁用状态作为实际限制手段记录；可操作入口确实被点击。两种实现均不额外规定为必须。依据 FR-05。
- E-06-04 `ui`：释放原请求后正常显示 P_A 和成功状态，不能用永远不再请求/永久锁死换取计数为 1。依据 FR-02、FR-05。

首次加载时若没有重试入口，记录该 UI 分支不可达；不伪造点击。已出现重试入口后的重复/混合操作由 TC-07、TC-08 验证。

### TC-07：重试 pending 时重复重试不并发

前置：通过真实加载请求注入 503，实际进入失败态；用户点击重试后，MR-RETRY-OK-B 保持新请求 pending。不能直接修改 UI/存储造出失败状态。

步骤：记录重试刚发出时请求数 R；在其 pending 时连续尝试三次重试；观察网络；release P_B。

预期：

- E-07-01 `network`：初始失败和首次重试规则均实际命中，首次重试确实是新请求。依据 FR-03、FR-04。
- E-07-02 `network`：重复动作后计数仍为 R，当前请求窗口最大在途数为 1。依据 FR-05。
- E-07-03 `ui`：重试入口若被禁用/隐藏，记录实际不可操作；可用则真实点击。释放后显示 P_B、成功状态和已清除的当前失败态。依据 FR-04、FR-05。

### TC-08：重试 pending 时点击加载不并发

前置与 TC-07 相同，确保已经存在真实重试请求，而不是只测首次加载。

步骤：记录 pending 重试的请求数 R；尝试“加载”，再交替尝试加载/重试；保持响应未返回直至这些动作完成；release P_B。

预期：

- E-08-01 `network`：初次失败及首次重试均实际命中；每个重复/混合动作后请求数仍为 R，最大在途数为 1。依据 FR-05。
- E-08-02 `ui`：加载/重试入口的可用或不可用状态记录完整；未绕过禁用控件触发应用方法。依据 FR-05 的真实 UI 验证要求。
- E-08-03 `ui`：原 pending 请求释放后展示 P_B 并成功，失败状态消失。依据 FR-04。

TC-06～08 的“三次”是用于发现重复触发的测试强度，不是业务阈值。要求针对整个 in-flight 窗口，不以某个固定防抖毫秒数代替。

### TC-09：非目标范围检查

`method: inspection`；`environmentId: profile-local-inspection`；`requiredAt: [feature]`。前置为可检查的实际候选和本次变更，当前尚未具备检查证据。

步骤：核对资料请求调用点、调度逻辑及本次增加的页面/权限处理，检查是否新引入重复定时请求或登录权限模型。必要时用受控时钟下的网络轨迹辅助调查，有限观察时间不作为“永不轮询”的完整证明。

预期 E-09-01 `document`：绑定候选版本的检查记录包含实际变更位置和判断，支持“没有引入自动轮询或登录权限模型”。依据 FR-07。不能用构建/lint 成功替代该项，也不能将失败的 browser TC 转移到本项。

## 5. 覆盖维度、边界和未纳入的预期

| 维度 | 本次处理 | 原因/限制 |
| --- | --- | --- |
| 成功 | TC-01；恢复成功 TC-02～05 | 明确有资料 JSON 和成功状态；真实字段待契约 |
| pending | TC-01、TC-06～08 使用受控 release | 无需虚构业务超时；可稳定观察请求尚未完成 |
| 失败 | 非 2xx 的 400、503、300 | 覆盖不同错误类别和上界外侧，避免仅对一种状态有效 |
| 恢复 | 真点击、真新请求、真新资料及错误状态消退 | 不以重试按钮存在代替恢复 |
| 重复与并发 | 首次加载、重复重试、加载与重试混合 | 阈值为已有 1 个在途请求时不允许第二个；0→1 的启动由 TC-01 覆盖 |
| HTTP 边界 | 300 明确应失败；200/299 是否构成合法成功响应待契约；204 空响应待 Q-03 | “非 2xx 失败”不能倒推任何 2xx 空体或不合法数据都成功 |
| 2xx 下界外侧 | 不把 199 构造成资料终态响应 | 1xx 是中间响应，不能把“pending/终态”混同；如实际代理存在特殊协议行为，再单独确认测试边界 |
| 合法空数据 | 保留 Q-03，未给通过 oracle | `{}`、`[]`、`null`、空 body 或“无资料”并不等价，均未由输入确认 |
| 网络断开 | 保留 Q-04；若确认纳入，精确路由 abort 后检查失败及真实恢复 | PRD 的泛称“请求失败”未列出网络故障表现，不能自行规定文案和策略 |
| 客户端超时 | 保留 Q-04；未指定时限，当前输入没有可依据的业务超时约定 | 未来确认后 hold 超过真实客户端阈值，观察应用超时；runner 超时或 `abort('timedout')` 不算客户端超时通过 |
| HTTP 200 业务失败/非法 JSON | 保留 Q-03、Q-04 | 未提供业务错误码或响应格式，不造 code/message 规则 |
| 部分失败 | 本设计不适用 | 只有一个确认端点，没有多请求/部分数据规则 |
| 权限/登录 | 不扩展权限模型 | PRD 明列非目标；若返回非 2xx，仍受一般失败要求约束，不编造跳转流程 |
| 跨标签页、刷新恢复、离开后持久化 | 未纳入 | 无此来源，不设置 storage/navigation 结果 |
| 视觉、移动端/设备人工检查 | 未建立必需用例 | 输入无视觉规范、设备矩阵或人工验收要求；不虚构人工通过 |

## 8. 本次设计中观察到的技能边界

1. Skill 开头要求读取 intake/delivery、测试约定及工作流文档，但没有单独说明“限定输入、仅设计、没有活动 feature”的降级路径。本任务按用户明确限制跳过这些材料，标记无法填写的字段，没有借机搜索其他项目资料或创建审批。
2. Skill 正确要求未部署端点先确认契约；遇到只有路径、源码不能作为契约的输入时，应允许先交付条件明确的设计，并把运行阻塞保留下来。当前文本没有给出这种不完整设计如何表达 `dataRef`、`contract.sha256`、`implementation.file` 的正式草案表示法，因此本文将其明确写为待补，未伪造 schema-valid delivery。
3. “全体 browser 环境需要 contract”及“完整读取已有状态链”偏向正式执行接入；本次不能据此创建不存在的运行环境或人为补齐确认。真正的业务阻塞是 Q-01，运行环境阻塞是 Q-05；它们不妨碍交付这份设计。

以上是实际使用时遇到的边界，不是对技能效果的通过评分。当前没有测试结果、后端联调证据或人工验收结论。
