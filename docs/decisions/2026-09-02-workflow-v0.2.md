# Frontend SDD Workflow v0.2 设计决策

> 历史决策：其中强制隔离 Worktree 的部分已被 `2026-09-02-real-project-workspace.md` 替换，其余多 Skills 与产物一致性原则继续保留。

## 目标

在不增加项目类型、框架版本和个人 Skill 配置的前提下，使工作流支持团队统一分发多个 Skills，并让每个需求 Workspace 关联一个隔离 Git Worktree。修改已生成产物时，受影响的下游产物必须在当前状态内同步更新，不通过回退状态重新执行整段流程。

## 已确认的边界

- 安装器全量分发仓库中的 Skills，开发人员不选择 Profile 或 Skill 组合。
- Skills 继续依赖各自的 `name` 和 `description` 由 Agent 正常判断是否触发。
- 不保存 Vue、React、Node 或包管理器的静态项目分类；Agent 读取目标仓库现状后决定命令。
- Workspace 保存需求产物、Worktree 元数据和代码变更记录。
- 代码只在隔离 Worktree 中修改；Workspace 通过 `project` 软链指向它。
- Worktree 使用本地分支，不自动创建 PR，不自动 push、merge 或 deploy。
- 工作流自身可以有发布版本，但不维护业务项目兼容版本矩阵。

## 方案演变记录

### Skills 分发

1. 初始版本只安装一个 `prd-to-code` Skill。
2. 曾考虑让每位开发人员自行选择和配置多个 Skills，但这会增加安装成本，并造成团队能力版本不同步。
3. 当前方案改为以仓库 `.agents/skills/` 为统一分发单元，一次安装或更新同步全部 Skills；触发仍由每个 Skill 的 `name`、`description` 和 Agent 的渐进式判断决定。
4. 暂不引入顶层 Skill 数量限制、Profile 或人工路由。只有当 Skills 数量和实际 token、延迟数据达到需要治理的规模后，再基于测量结果优化。

### Workspace 与代码

1. 初始设想是 Workspace 只保存文档产物，代码直接在真实项目中修改。
2. 曾讨论让隔离分支通过额外 PR 完成 Review，但这会重复团队现有 Review 流程，也可能让隔离环境与开发人员当前本地配置产生差异。
3. 当前方案保留隔离 Worktree 作为代码修改区和可追溯对象，Workspace 用软链关联它并记录 Diff、修改文件和验证结果；工作流不创建额外 PR，开发人员仍在真实项目环境中完成最终效果审核和集成决策。

## 结构

```text
.ai-dev/
├── changes/<change-id>/
│   ├── status.json
│   ├── worktree.json
│   ├── code-change.md
│   ├── project -> ../../worktrees/<change-id>
│   └── 其他 SDD 产物
├── worktrees/<change-id>/
├── artifact-graph.json
└── scripts/
    ├── init-worktree.mjs
    └── update-consistency.mjs
```

`.ai-dev/worktrees/` 和需求目录中的 `project` 软链属于本地执行环境，由 `.ai-dev/.gitignore` 排除。需求文档、`worktree.json` 和 `code-change.md` 保留为 Workspace 记录。

## 多 Skills 分发

安装器以 `.agents/skills/` 为整体来源，不再硬编码 `prd-to-code`。`install` 和 `setup` 都复制其中的全部 Skill 目录；`doctor` 检查 Skill 根目录，并要求每个直接子目录存在 `SKILL.md`。

## Worktree 生命周期

1. 完成计划审核后创建 Worktree。
2. 默认本地分支名为 `sdd/<change-id>`。
3. Worktree 位于 `.ai-dev/worktrees/<change-id>`。
4. 在需求 Workspace 中创建相对软链 `project`。
5. 记录源仓库、基线分支、基线提交、Worktree 路径和创建时间。
6. Agent 读取 Worktree 内的仓库文件，选择已有安装、测试和构建方式。
7. 最终审核后保留 Worktree，交由开发人员决定本地合并或清理。

## 产物一致性

`status.json.state` 表示当前工作阶段，产物刷新不修改它。`artifact-graph.json` 定义产物依赖；`update-consistency.mjs mark <artifact>` 计算传递下游、标记过期产物并清除受影响的历史审批。Agent 更新下游产物后使用 `resolve` 清除对应过期标记。

任何审核点和最终完成状态都要求 `staleArtifacts` 为空。这样可以保留当前阶段，同时阻止旧技术方案、旧任务或旧验证结果继续被当作有效上下文。
